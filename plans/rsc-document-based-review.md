# RSC Document-based Review 计划

## 目标与范围

以原文 batch 为独立任务，并行检查原文要求是否充分体现在已提取实体、fields 和 processing 中。将 uncovered 列表与现有 Fix prompt 一起提供，补充确定性校验无法发现的语义遗漏。

- 在 `states`、`steps`、`step_dependencies` 三个类别扫描结束后的类别 Fix 流程中执行。
- 每轮使用最新注册表重新审查全部 batch，包括首次进入类别校验时；不能因为确定性 issue 为零而跳过。
- 全局 Fix 不执行 document-based review；全局校验和发布继续使用现有确定性校验规则。
- 保持简洁实现，复用模型配置、来源索引、日志、检查点及 Fix 调度，不增加 MCP 工具。

## 审查范围与上下文

| 当前类别 | 检查的实体类别 |
| --- | --- |
| states | parties、channels、messages、states |
| steps | parties、channels、messages、states、steps |
| step_dependencies | 全部六类，包括 step_dependencies |

每个 batch 使用全新、只读的 LLM 上下文，不继承 Scan/Fix 对话历史，不提供 MCP 工具。输入包含：

1. 当前 batch 的完整原文片段、document ID、batch ID 和章节/block 定位；不发送整份 RFC。
2. evidence block 与当前 batch 重叠、且属于本次检查类别的所有有效实体。按实体 ID 去重，保留完整定义、fields 和 processing，不限制实体数量、不摘要实体定义。
3. 实体的名称、别名和证据定位等必要关联信息；不重复展开 evidence 原文，不发送实体操作历史和完整引用边，不附带无关 unresolved。
4. 已扫描类别的全局名称及别名简表，帮助区分实体缺失与来源关联不足；简表不重复完整实体内容。
5. 当前检查类别、建模范围和启用扩展。

不使用面向交互查询的完整 `entity_details` 返回值直接拼接输入，避免额外展开证据原文与引用边。复用 evidence block 与 batch 的关联判断，专门组装审查所需投影。

提交前计算原文、实体、提示词和输出预留的 token 预算。超过现有模型预算时报错并保存进度，不静默截断原文或实体。首版沿用冻结的 batch 计划，不引入额外自动分块系统。

## 提示词与输出

审查提示词使用通用描述，不包含某个特定协议或消息的示范，要求逐段对照原文检查：

- 缺失的角色、通道、消息、字段、状态、动作及依赖。
- 概览实体未被详细章节补充的定义、编码、字段与条件。
- 发送端计算、接收端解析与验证、状态读写和输入来源。
- 默认行为、成功/失败分支、约束、生命周期及版本和扩展适用条件。

只报告当前检查类别内、且有当前原文直接依据的遗漏。不得仅因实体未出现在 batch 关联列表就认定全局缺失；无法从输入确认的细节不臆造为缺口。

使用 Pydantic 结构化输出：`uncovered` 按实体类别组织，每类为自然语言字符串列表。每条简短说明缺什么以及属于哪个对象或交互；字段遗漏放在 messages 类别，并说明所属消息和字段。没有遗漏时返回空列表。

宿主补充 batch/document 来源。按类别和去除首尾空白后的相同文本去重，保留全部来源；不同表述保留，不增加 LLM 合并调用。不为这些条目增加 agent 生成的 ID，也不自动写入 unresolved。

## 并行调度与 Fix 接入

- 每个 batch 一个独立并行 API 调用，继承 Scan/Fix 的 provider、model 和 effort；同时调度全部 batch，不设置固定为 4 的应用并发限制。
- 所有 document-review 请求共享一个进程内限速器，默认 5 次/秒，由 `document_review_requests_per_second` 配置（默认 5，必须为正数）。限速作用在实际 API 请求发送前，按请求间隔节流，不限制并发任务数量；provider 重试的请求同样计入。实现使用异步等待，复用现有超时/取消机制，不阻塞事件循环，也不改变 Scan/Fix 的请求策略。
- 审查期间使用冻结的只读注册表，全部任务完成后整合结果，再启动一个现有 Fix agent 修改注册表。
- Fix 初始上下文新增 `document_review`，包含完整 uncovered 列表及来源，同时保留现有确定性 issues、unresolved 和可写类别说明。
- 提示词要求尽力修复全部 uncovered，回查相关原文、补全或修订已有实体，并保留有效字段、processing、条件和分支。
- `complete_fix` 仍表示提交一轮修改。宿主接收修改后，重新执行确定性校验与所有 batch 的文档审查；二者均为空才判定该类别通过。
- 不把缓存的 uncovered 数量直接套入现有确定性 issue 的下降判断。文档遗漏只能在下一次独立审查后确认消失，不能因 agent 声称已修复而清除。
- `validate_entities`、`complete_fix` 附带最近一次 `document_review`；修改后标明该结果尚未复审。工具内部不新增 API 审查。
- 沿用类别 Fix 轮次上限。到达上限后按现有机制继续后续类别，保存剩余 uncovered；后续类别会对其已扫描范围重新检查。
- 未清空的类别 uncovered 作为修复参考传入全局 Fix，并保留来源与最后审查阶段；全局 Fix 不重新审查，也不将其自行标记为经文档复审通过。这些历史结果不作为全局发布的新增阻断条件。

## 配置、恢复与日志

- 增加 `document_review_enabled`，默认开启；不增加独立审查模型配置。
- 增加 `document_review_requests_per_second`，默认 5，校验为正数；只作用于新增的 document-review 调用。
- API 请求超时和重试次数沿用现有设置，整体计入运行硬超时。限流、超时、非法输出均不等同于零遗漏；重试耗尽后保存进度并报错退出。
- 将每轮审查的逐 batch 结果、完成状态与其输入注册表快照关联，记录在内部检查点中；恢复时仅复用同一快照已完成的结果，重试尚未完成的 batch。
- 复用 JSON 检查点与原子写入，不引入数据库、hash、digest 或实体 revision。新类别轮次和注册表修改使旧结果失效；旧检查点无审查记录时执行审查。
- 复用完整 request/response 日志，每阶段、类别、轮次、batch 一个 JSONL 文件。记录逐 batch 耗时、整轮墙钟时间、调用次数、token 用量和各类 uncovered 数量。
- 最终产物仍为 `protocol.json` 和 `unresolved.json`，审查结果留在内部检查点与日志中。

## 实现与验证顺序

1. 新增简洁的审查输入组装、输出类型及只读调用模块，复用现有来源和模型日志能力。
2. 接入后三类的类别校验/Fix 循环，处理零确定性问题但有 uncovered 的路径；全局 Fix 仅接收遗留参考列表。
3. 补充检查点恢复、配置、统计与工具返回信息，更新使用说明。
4. 运行现有测试，增加有意义的行为验证：完整实体去重、无证据原文重复展开、检查范围、真实并行、遗漏触发 Fix、修复后重新审查、失败重试、过预算、中断恢复及轮次上限。
5. 专门验证全局 Fix 不触发文档审查，且历史 uncovered 不被伪装为新模型的审查结论。
6. 使用现有 FTP 和 TLS 多 RFC 集合各运行一次 Luna high，硬超时各 2h，通过 hc 启动。记录审查成本、Fix 轮次、uncovered 变化与整体耗时；对照原文人工抽查发现和修复的缺口。不重跑旧流程。

验收要求：语义遗漏能独立触发类别 Fix；结果只能由重新审查更新；失败 batch 不丢失；输入不静默截断；全局 Fix 不执行文档审查；最终结构校验、日志与恢复行为保持正确。
