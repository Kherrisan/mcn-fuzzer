# RSC 按章节局部性并行解析、并行审查与增量复审

## 1. 目标与整体流程

在当前已精简的代码上实现：

```text
确定性预处理
    ↓
按章节生成 source batches，均衡划分连续区间
    ↓
3 个 parser 并行生成局部草稿
    ↓
确定性合并 → 处理语义冲突与跨范围依赖
    ↓
冻结全局模型
    ↓
3 个 reviewer 并行执行原文审查与跨范围审查
    ↓
汇总 findings
    ├─ 全部通过 → 发布
    └─ 需要修复 → 并行 fix → 合并 → 增量复审
```

默认配置与边界：

- `parse_workers=3`、`review_workers=3`，可配置为正整数；两个阶段分别运行，默认最多三个模型会话同时工作。
- 将 agent 可见 MCP 工具从 **18 个收敛到 13 个**，按角色和阶段提供必要目录；确定性的预处理、状态观察和 gate 检查保留为服务内部能力。此项替代之前固定保持 18 个工具的约束。
- 保持最终 `protocol.json` 格式；面向 agent 的任务和对象使用 name，不引入新的 hash/digest 标识。
- 保留来源覆盖、证据、schema/reference、独立 review 和 resolution 验收。
- 本次实现增量复审；不恢复已经删除的来源预计划、reviewer 提前准备和共享笔记机制。
- 新任务使用新状态结构；旧实验任务使用原源码快照恢复执行，当前版本保留历史审计能力。

## 2. Source batch 划分、分配与模型合并

### 统一工作单位

**Source batch 同时作为来源覆盖、提取完成和原文审查的基本单位，不再另外包装通用 task。** Worker 的 assignment 直接包含有序的 batch 列表。

- 复用现有有界 source batches、完整阅读凭证和逐批报告。继续使用现有 `batch_target_tokens=8000`、`batch_max_tokens=12000`，预算包含来源交付元数据；不新增 `parse_task_target_tokens` 或 `parse_task_max_tokens`。
- 按用户传入的文档顺序、文档内章节和原文位置排列完整 batch source list。
- 生成 batches 时优先保留章节局部性，超大章节沿连续子章节、段落边界拆分，单段过长时沿 Unicode 字符边界拆分；全部非空原文恰好归属一个 batch。
- 阅读工具一次可以交付多个完整 batch，按预算分页；分页是传输行为，不增加工作实体。
- 完成状态按 batch 和阶段记录；同一个 batch 的 parse 完成与 review 完成分别验收。

### 接近等量的连续区间分配

- 设 batch 数为 N，实际 parser 数为 `min(parse_workers, N)`；没有正文时预处理直接报错，不创建空 assignment。
- 每个 batch 的权重为其原文 token 数。使用连续区间划分，而非轮询分发，确保每个 parser 获得原列表的一段连续子列表。
- 先求最小的最大区间权重 M，再在最大权重不超过 `1.10 × M` 的连续划分中，优先减少同一章节内部的切点，其次减少同一文档内部的切点；仍相同时按切点索引字典序选取。由代码确定，使用整数比较避免浮点边界差异。
- 这里的接近等分指原文 token 总量接近，不要求 batch 个数相同。不能拆开现有 batch 来凑等分；单个大 batch 造成的负载差异如实报告。
- 第一版一次性固定分配，parser 按自己列表的原文顺序处理，完成后不抢占其他 parser 的 batches。这样保持章节上下文，避免引入动态任务队列。
- 每个 parser 共享一份覆盖其全部 assigned batches 的局部草稿与 revision，不为每个 batch 单独建草稿。
- 允许跨文档的连续区间；当文档边界能满足上述负载限制时优先沿文档边界切分。
- 故障恢复可将确认失败 worker 尚未完成的 batches 及其局部草稿整体移交给一个替代会话；撤销旧 attempt 后再派发，不让两个进程同时写同一草稿。

例如，若 12 个 batches 的长度接近，三个 parser 可以分别获得 `b1—b4`、`b5—b8`、`b9—b12`；长度不同时调整连续切点，不拆成奇偶或轮询列表。

### 局部草稿与跨范围依赖

- Parser 只修改自己 assignment 的草稿，其他 worker 提交不会使自己的 revision 失效。
- Parser 可查询已封存草稿及名称索引；活动草稿不作为稳定依赖。
- 所有 parser 可以补读任意相关 batch，不等待其负责人完成。补读只提供上下文和证据，不改变主负责人，也不能替对方提交完成报告。
- 每条局部记录必须通过自身 schema 和证据检查，允许在合并前保留跨 assignment 的悬空引用。
- 每个 batch 的完成报告包含实际提取结果及待整合关系：相关来源、对象名称和需要满足的约束，不另设预计划报告。
- 未完成的提取工作不能以 unresolved 代替；unresolved 只表达有证据支持的原文歧义。

### 合并与冲突

整个阶段操作一份合并候选，按“代码建立候选及初始清单 → 合并 agent 处理 → 代码复查 → 冻结”执行。复用一个 parser 会话处理需要语义判断的事项，不额外启动阅读全文的冲突发现 agent。

#### 步骤 1：封存输入

- 所有 parser 完成 assigned batches 后，封存每份局部草稿及 revision、逐批提取报告、原文证据和待整合的跨范围关系。
- 合并期间禁止继续修改这些输入。原始草稿和报告保留用于追溯，合并候选及其关联视图单独更新。
- 按原文顺序读取封存结果，保证合并初始结果不依赖 parser 的完成先后。

#### 步骤 2：建立候选和引用关系

- 具名对象使用“原始 parser/assignment 范围 + kind + 局部 name”区分。例如 `parser-1 / messages / USER` 与 `parser-2 / messages / USER` 在完成判断前是两个候选；范围信息不进入最终协议名称。
- 局部引用优先绑定所属草稿中的定义；缺少本地目标时查找其他草稿。同名候选有多个时保留歧义，不能按到达顺序选择。
- 建立结构化引用的反向索引，覆盖 step 的 party/message/channel 引用、dependency 两端、字段关系及报告中的对象关联。
- 维护局部对象到最终对象的映射，由服务端保存，不要求 agent 手工维护额外 ID。

#### 步骤 3：自动合并严格相同的记录

- 按 party、message、channel、step、dependency 的依赖顺序处理；仅在所引用对象已经唯一绑定时判断引用方是否重复。
- 相同 kind、相同 name、相同内容的定义保留一份并汇总原文证据；比较不包含证据集合，但不能忽略定义字段差异。
- 完全相同且引用相同最终对象的 dependency 去重并合并证据。条件或字段关系不同的 dependency 保留，不能自动推断等价或矛盾。
- 同名不同内容保留所有候选并记录待处理项。不同名的定义暂时保留，不通过名称相似度自动合并。
- 前面的名称和引用统一后，重新检查受影响的下游记录，直到没有新的确定性重复项。每轮变化均可审计、可恢复。

#### 步骤 4：由代码建立初始冲突清单

| 情况 | 代码负责的发现与记录 | LLM 负责的判断 |
|---|---|---|
| 同名不同定义 | 比较候选并列出实际差异字段 | 判断提取错误、等价表达或应分别命名的不同概念 |
| 引用目标不存在 | 记录引用位置及期望对象类型 | 关联已有定义，或依据原文补充遗漏 |
| 引用有多个候选 | 列出所有候选及引用方 | 确定实际指向，必要时分别命名 |
| 已声明结构约束不一致 | 运行现有 schema/reference/连接角色检查并记录问题 | 判断该改定义、引用还是提取结果 |
| Parser 报告的待整合关系 | 汇总未完成事项及其相关来源、对象 | 补齐来源支持的跨范围约束与依赖 |
| 不同名同义、自然语言条件矛盾 | 不声称能完整自动发现；记录 agent 后续发现的问题 | 合并 agent 在相关上下文中判断，独立 reviewer 继续检查 |

- 每个清单项包含：类型、相关对象及局部范围、候选定义、差异或引用位置、受影响记录、原文证据，以及处理状态和决定。
- “同名不同内容”表示需要判断，不自动断言某份定义错误。例如两个 `data_channel` 的 initiator 不同，可能分别描述主动、被动连接，应分别命名。
- 清单不是语义问题的完整枚举。代码只记录可确定的结构问题和 parser 已明确报告的事项，不先让 LLM 阅读全文生成一份额外清单。

#### 步骤 5：合并 agent 集中解决

1. 领取合并 assignment，通过 `query_model` 分页读取候选、冲突清单和相关引用；查询固定到当前候选 revision。
2. 使用 `read_batches` 完整补读作出判断所需的原文，必要时使用 `search_source` 定位后再补读。
3. 决定保留、合并、分别命名、修正引用或补充遗漏定义/关系。决定附来源依据；不以缺少实现时间解释 unresolved。
4. 通过 `apply_changes` 提交具名修改或合并/重命名操作，由服务端校验并执行。
5. 服务端重新计算受影响的结构问题和剩余事项，返回新 revision、更新后的名称及 blockers；agent 持续处理到可提交。

该 agent 处理候选和问题涉及的上下文，不重新生成整份协议。原文确有歧义时，可以提交有证据支持的 unresolved 及对应模型表示，但不得留下无法解析的结构引用；该决定仍进入后续独立 review。

#### 步骤 6：原子更新名称、引用和报告关联

- 在 `apply_changes` 的具名操作数组中增加仅合并阶段可用的 `merge` 和 `rename` 操作，工具数量仍为 13。源对象必须明确局部范围，不能对所有同名字符串做全局替换。
- `merge` 明确指定源候选、最终名称/定义及来源依据；`rename` 明确指定单个候选和新名称。服务端展开全部结构化引用更新，agent 无需手工枚举每个引用方。
- 同一事务完成最终定义写入、证据保留、引用改写、重复候选移除、名称映射和合并决定记录。目标名称冲突、来源不合法或更新失败时整批回滚。
- Step 重命名同时修改 dependency 两端；message 重命名修改 step 的消息引用及适用的字段限定名；party/channel 重命名更新对应 schema 引用位置。
- 原始来源报告保持封存，通过映射更新合并后的报告关联视图，确保已完成 batch 仍能追溯其最终模型记录。原有证据不因重命名丢失。
- 自由文本中的名称不作盲目字符串替换；可能受影响的条件/说明返回给合并 agent 核对，明确完成后才关闭相关事项。
- 保留候选 revision 检查和操作幂等；重试同一决定不会再次删除候选或重复改写引用。

例如确认 `parser-1 / messages / USER` 与 `parser-3 / messages / UserCommand` 表示同一个 FTP USER 命令后，统一为 `USER`，汇总两份证据，将相关 step 的 `message_name` 和报告关联指向最终对象；名称相近本身不足以授权合并。

#### 步骤 7：验收并冻结

- 全部 batch 已完成实际提取，所有结构冲突和已登记的跨范围事项得到处理。
- 名称唯一、引用无缺失或歧义，schema、字段关系及连接角色校验通过。
- 来源证据和报告关联完整，合并操作未丢失追溯信息；原始封存数据保持可审计。
- `advance_phase` 提交合并结果，协调器通过内部 gate 后冻结一个全局 revision，启动并行 review。

结构冲突清零只说明整合完成，不代表语义审查通过。不同名同义、未被 parser 标记的跨章节遗漏和隐含条件矛盾仍由独立 reviewer 检查。Fix 后的 patch 合并复用同一机制，并触发相应审查结论失效。

## 3. Review、Fix 与增量复审

### 审查组织

Review 在冻结模型上执行两类检查；原文检查直接复用 source batch，跨范围检查保留独立的审查条目：

| 类型 | 责任 |
|---|---|
| 原文审查 | 独立检查负责来源中的要求是否完整、准确地表达在模型中 |
| 跨范围审查 | 检查共享定义、跨 assignment 关系、生命周期、条件和字段关系的一致性 |

- 原文审查将同一个 batch source list 按 reviewer 数使用上述连续均衡分区规则分配，结果不必与 parser 分区相同；每个 batch 有唯一主审 reviewer。
- 关联模型由证据、对象引用和 parser 报告的跨范围关系共同确定，包含相关定义和引用闭包。
- 跨范围审查条目根据实际模型连接及待整合关系生成，附加到相关 reviewer 的 assignment。优先归属所涉最早 batch 的主审 reviewer；没有来源关联的模型条目分配给当前检查条目最少的 reviewer，相同时按 worker name 排序。相互关联的检查组合处理，不另建通用任务队列。
- Reviewer 获得全局名称索引，并可查询完整模型和补读来源。不能仅依据 parser 提供的引用判断遗漏。
- 审查报告记录原文要求、实际核对的模型、结论和 findings；这些是实际比较结果，不要求先进行独立的需求提取阶段。
- 不对外暴露 parser 的推理作为证据；reviewer 依据原文与冻结模型独立判断。

### 验收条件

将当前“一个 reviewer 读取整个模型”的 gate 改为：

- 全部来源范围有实际审查报告。
- 全部模型记录有明确审查归属，跨范围关系完成检查。
- 每个 batch 和跨范围审查条目均完整交付其负责来源和必要模型上下文。
- 所有 findings 的 resolution 均得到独立验收。
- 所有提交对应正确的冻结版本和 assignment attempt。

阅读凭证只证明交付，不自动生成通过结论。Reviewer 无权修改模型。

### 修复与增量复审

- Finding 包含原文要求、当前差异、影响对象和修复验收条件。
- 按关联 findings 组合修复范围并分配给 parser；已知写入对象重叠的修复范围组合处理，互不冲突的范围并行生成 patch。修复依据 findings，不强行伪装为 source batch，也不增加统一 task 表。
- Fix 不直接修改共享模型。合并 patch 时检查其基础版本与实际写入集合，发现新的重叠则加入合并冲突清单。
- 每个审查结论记录依赖的来源、模型记录、关联关系和查询范围；缺失判断也必须记录其搜索范围。
- 修改后传播失效：删除或重命名影响相关引用；共享定义修改影响使用方；新增记录影响对应范围的缺失判断。
- 未失效结论经依赖一致性检查后沿用；失效 batches 和跨范围审查条目在新冻结版本上重新审查。
- 自然语言条件的影响无法可靠确定时扩大审查范围；仍不确定时回退全量 review，不以不完整的图依赖推断语义独立。
- 保留 review 轮数限制及现有部分发布语义；未完成的 batch 报告或审查条目、工程冲突或未通过硬校验不得发布。部分发布不算性能验收通过。

## 4. 状态管理、MCP 与 Agent 工程实现

### 实现原则：简洁、适度抽象与跨阶段复用

- 采用简洁、直接、易读的代码，以当前已确定的需求为边界。优先使用清晰的数据结构和普通函数，不为假设中的扩展引入通用任务框架、插件层、多级继承或额外配置开关。
- 改动前阅读相关模块，优先整理和复用现有实现；替换旧路径时同步清理失效的分支、配置和提示词，避免累积多套实验实现。
- 按实际共享职责组织模块，不为 Parse、合并、Review、Fix 各复制一套基础设施。Assignment 生命周期、worker 启动与恢复、来源读取与凭证、版本/权限校验、事务及幂等处理应由各阶段共用。
- Parse 草稿合并与 Fix patch 合并复用引用索引、冲突检测、名称映射、原子更新及冻结校验；首次 Review 与增量复审复用上下文查询、审查报告、finding/resolution 验收和覆盖检查。
- 阶段差异通过少量明确的参数、权限规则和阶段处理函数表达。共享机制不得抹平阶段语义，例如提取报告不能代替审查结论，parser 不能自行验收修复。
- 仅在出现实际重复逻辑时提取公共模块，保持接口小且职责明确；不追求将所有阶段强行抽象为同一种流程。代码审查同时检查不必要的抽象、重复实现和可删除的兼容分支。

### 持久化和并发控制

重点改造现有 workflow 状态机、supervisor 和 agent adapter，不新增平行实现。

- 将全局唯一 assignment 拆成每 worker 一份持久化 assignment，记录 name、role、batch 列表、attempt、基础版本及状态。Source batch 复用现有标识和范围；不另建 parse/review task 表或 task name。
- Assignment 记录派发、领取、提交和失败状态；batch 分别记录提取及审查进度。Agent 提交逐批报告并提交当前 assignment，协调器检查全局条件后推进阶段。
- 使用一个 MCP 服务和一个 SQLite 写入入口。Assignments、batch 阶段进度、worker 草稿、冻结快照、审查结论分别存储，避免每次操作重写整个任务 JSON。
- 数据库写入采用短事务；模型推理、hc 调用和大页序列化不持有写锁。
- 查询固定到不可变版本；写入验证 assignment attempt、权限和预期 revision。
- 幂等操作绑定 assignment、attempt 和 operation_id；重复请求返回原结果，参数改变则拒绝。
- Assignment 重新派发后撤销旧 attempt，拒绝旧进程的迟到写入。
- Supervisor 与 MCP 重启时根据持久化状态恢复，不依赖终端文字推断成功。

### 工具使用证据与优化目标

历史统计见 [`tool-usage-audit.json`](../rsc/benchmarks/ftp-runtime-stability/tool-usage-audit.json)。早期 32 分钟的完整运行用过全部 18 个工具，后续 24 次实验包含提前停止和超时，不能用低调用次数推断某项验收能力可以删除。

- 后续实验的 `read_batch`、`search_source`、`review_resolutions` 均为零次；单批读取可由批量工具覆盖，跨范围搜索及独立修复验收仍然必要。
- `workflow_status` 共 1,049 次，其中 1,025 次来自 supervisor；另外 24 条包含 CLI 健康探测，不能归为 LLM 轮询。后续指标明确区分 agent、supervisor 和健康探测来源。
- `complete_review_batch` 共 183 次，其中 179 次属于已删除的来源准备阶段，正式 review 为 4 次批量调用。
- `apply_changes` 的 359 次调用有 61 次被拒绝，约 17%；历史错误涉及字段类型、列宽、证据和选择器。该统计跨多个实现版本，不视为当前版本的错误率。

工具优化用于减少接口理解成本、重复调用和错误往返。整体性能仍按完整 parse、review、fix 计时，不从工具数量减少推导耗时达标。

### 收敛到 13 个 agent 工具

| 现有工具 | 调整及约束 |
|---|---|
| `read_batch` | 合并进 `read_batches`；单批读取传长度为 1 的 batch 列表，保留完整交付和 receipt 校验 |
| `prepare_sources` | 改为协调器内部预处理调用，保留来源冻结和覆盖校验 |
| `workflow_status` | 保留为协调器和诊断接口；agent 所需 assignment、版本、剩余 batches 和允许操作随领取及提交结果返回 |
| `check_gate` | 改为内部校验；提交时执行并返回完整 blockers，保留全部硬校验 |
| `complete_review_batch` | 合并进 `complete_batch`；由服务端角色、阶段和 assignment 决定报告规则，分别记录提取与审查结果 |

最终 agent 工具目录共 13 项：

1. `claim_assignment`
2. `advance_phase`
3. `list_batches`
4. `read_batches`
5. `search_source`
6. `query_model`
7. `get_changes`
8. `apply_changes`
9. `complete_batch`
10. `list_findings`
11. `submit_findings`
12. `submit_resolutions`
13. `review_resolutions`

- `complete_batch` 在 parse 阶段提交提取报告，在 review 阶段提交实际来源/模型比较结论；不能将 parse 报告自动计为 review 通过。
- 保留 `submit_findings`，允许 reviewer 在全部审查完成前提交问题；保留 `review_resolutions`，只允许独立 reviewer 接受或拒绝修复。
- `search_source` 支持并行后的跨范围定位，搜索结果仍不能代替要求的完整来源阅读。`get_changes` 用于修复和后续复审。
- `advance_phase` 保留显式 assignment 提交语义，服务端执行完整 gate；只有协调器可以推进全局阶段，不因最后一份 batch 报告到达而自动发布。
- 新 agent 目录移除旧单批读取和独立 review 报告入口；历史记录的解析与离线审计继续识别旧工具名称，旧实验恢复执行使用原源码快照。

### 按角色和阶段提供目录

- 尚未领取 assignment 时提供领取入口；领取响应给出 batch 列表、版本、当前进度和允许调用的工具。
- Parse/整合提供来源读取、模型查询、修改和必要报告/提交工具；fix 增加 findings、diff 和 resolution 提交能力。
- Review 提供来源读取、模型查询、问题与审查报告提交工具；后续复审增加 diff 和 resolution 验收能力。Reviewer 始终没有 `apply_changes` 权限。
- 实现并验证 MCP 工具目录变更通知。对缓存目录且不能刷新阶段工具的客户端，使用角色所需工具的并集，当前阶段允许列表随 assignment 返回；服务端始终逐次校验阶段和权限。
- 移出 agent 目录的内部接口使用协调器身份，agent 不能通过手工构造调用绕过目录限制。

### 简化参数格式与错误反馈

- 新 `apply_changes` 接口统一使用具名记录数组 `changes=[...]`。每条记录按 op 明确声明 kind、target、value、evidence 或删除原因等适用字段；不再同时向新 agent 提供列式、分组、共享默认值等多种编码方式。
- 保留有用的 add/update/patch/delete 语义，优先使用现有精确名称选择器；数组字段的 patch 仍整体替换。简化输入编码不能取消证据、引用、版本和幂等校验。
- 合并阶段额外允许同一具名数组中的 merge/rename 操作，服务端负责展开引用及报告关联更新；普通 parse、fix 和 reviewer 不获得这些阶段权限。
- 来源和模型交付统一使用具名 records，避免 agent 在位置列与字段名之间转换；历史 compact 数据的离线审计继续保留。
- 对可以独立检查的多个错误一次返回精确位置、原因及当前 revision；存在任何错误时整批回滚，不静默补字段、选取歧义目标或跳过失败行。
- 领取结果返回来源分配信息，写入结果返回记录名称、revision 和草稿引用问题，提交结果返回剩余工作与 blockers，减少为获取已知状态而额外查询。

### 工具与并行状态的衔接

| 工具组 | 调整 |
|---|---|
| `claim_assignment` | 返回具名 assignment 及连续 batch 列表，原子检查 worker 归属 |
| 来源读取工具 | 区分负责来源与补读；凭证绑定 worker、assignment、attempt |
| `query_model` | 支持当前草稿、封存草稿索引、合并候选及冲突清单、冻结模型视图；均按版本分页 |
| `apply_changes` | 普通 parser 只写 worker 草稿；合并阶段指定 parser 可修改候选、提交 merge/rename 并原子更新引用 |
| `complete_batch` | 按阶段提交实际来源结果、跨范围关系或独立审查结论 |
| Finding/resolution 工具 | 绑定审查版本、batch/审查条目和修复范围 |
| `advance_phase` 与内部 gate | 区分 assignment 提交与协调器阶段推进权限，拒绝时返回完整 blockers |

- 权限由凭证和持久化 assignment 决定，客户端参数不能扩大权限。
- 协调器使用独立凭证，不再借用普通 parser 身份执行全局调度。
- 不允许跨 worker 或重新派发的 attempt 复用来源阅读凭证。
- 复用现有批量调用、分页、名称选择器、原子回滚和错误定位能力。

### hc 与会话接入

- 使用 **hc** 启动和控制 worker，复用现有 Codex/Pi adapter；agent 不自行派生子 agent。
- 将 role 与 worker name 分离，每个 worker 独立目录、凭证、MCP namespace、日志和会话。
- hc terminal 与 Codex thread 使用相同名称，例如 `rsc-<任务名>-parser-1`。
- Codex 指向真实 executable，保留跳过更新检查；保留仅执行 `exec` 的启动器，不增加安装或更新逻辑。
- 启动时串行完成共享状态初始化和会话 ready 检查，再并行派发 assignments，避免首次 SQLite 初始化竞争。
- 阶段内复用会话；阶段切换保存会话信息并释放进程，需要 fix 或再次 review 时恢复。
- Supervisor 公平处理全部 worker，单次 `hc wait` 不阻塞其他任务派发。
- 先持久化发送意图，再执行 `hc send`；MCP claim 才是 assignment 接收确认。
- 观察超时不直接触发重派。确认原进程终止并撤销旧 attempt 后，才恢复或重新分配。
- 确认的进程/传输故障每 assignment 最多自动重试两次；持续失败保留现场并报告，语义问题继续正常修复流程。
- `workers=1` 使用同一架构，作为调试和性能对照，不维护另一套串行流程。

## 5. 实施顺序与验收

按以下顺序交付，每步先通过相关测试：

1. **Assignment 基础设施与工具收敛**：存储版本、worker 身份、batch 列表与阶段进度、权限、attempt、幂等和恢复；落实 13 个工具、内部协调器接口和具名参数格式，先以单 worker 运行完整流程。
2. **章节调度与并行 Parse**：source batch 列表按 token 均衡切成连续区间、章节边界优先、局部草稿、跨范围补读、合并及冲突处理。
3. **并行 Review**：原文审查、跨范围审查、覆盖归属和新的阶段 gate。
4. **并行 Fix 与增量复审**：patch 合并、结论依赖、失效传播和全量回退。
5. **真实运行与文档**：配置示例、工具契约、迁移说明、恢复说明和测量结果。

必要测试：

- 章节局部性、超大章节拆分、原文覆盖、连续均衡分区、batch 唯一归属及故障替换。
- 多 parser 并发提交、不同完成顺序、同名冲突、悬空引用、原子重命名及证据保留。
- 验证候选保留局部名称范围；相同字符串指向不同局部对象时不误合并；上游定义统一后能够发现下游重复，而不同条件的 dependency 继续保留。
- 验证初始清单准确列出字段差异、缺失/歧义引用、结构约束和已报告的跨范围事项；同名差异不直接判错，不把不同名同义或自然语言矛盾声称为已自动排除。
- 验证 merge/rename 的阶段权限、目标冲突、引用与报告关联原子更新、失败回滚、幂等恢复和自由文本待核对项；封存的原始草稿及报告保持不变。
- 跨 worker 越权、凭证误用、旧 attempt 迟到、重复提交、发送丢回复、服务重启及合并中断。
- Reviewer 独立发现遗漏、跨章节语义冲突、全部模型审查归属以及未完成的 batch 报告或审查条目阻止发布。
- 增量复审保留无关结论，正确失效共享依赖和缺失判断；修复引入的新问题可被发现。
- 校验全部 13 个 agent 工具 schema，以及角色/阶段目录刷新和缓存客户端的权限限制；验证旧工具名称仍可用于历史审计，但不能通过新 agent 入口执行。
- 验证 `read_batches` 单批/多批的交付与 receipt 等价性，统一 `complete_batch` 仍严格区分 parse/review，内部 gate 和独立 resolution 验收不能被绕过。
- 验证具名 mutation 数组的增删改、精确选择器、错误汇总、整批回滚与幂等重试；新客户端不再需要列宽、证据池索引或分组默认值编码。
- 模拟 hc 验证公平调度、启动初始化、会话命名、恢复和限次重试；确认预处理和状态观察不消耗 agent 工具往返。

真实验收使用固定 RFC 959、RFC 3659 和 `gpt-6-luna/high`，新输出目录运行 **3 次**。目标为完整通过并争取 **20 分钟以内**；单次诊断上限 **40 分钟**，避免只记录 parse 耗时而丢失复审结果。

报告总耗时、各阶段关键路径、worker 利用率、重复阅读量、合并耗时、冲突数、返修轮数、重审范围、token 用量及语义验收结果。工具调用按实际来源、阶段、成功/拒绝分类，同时记录目录规模、参数错误和重复查询；批量调用次数与其处理的报告数量分别统计。超时、部分发布和未通过语义检查分别记录为失败。未达到 20 分钟时交付实际结果与瓶颈，不自动进入无限优化循环。
