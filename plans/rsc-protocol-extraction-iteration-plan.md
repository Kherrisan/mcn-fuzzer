## 目标

反复执行「分析结果 → 修改并提交代码 → 并行复测 → 分析新结果」。RTSP、SIP、TLS 各自须在**每协议 60 分钟以内**完成提取和发布；60 分钟同时是目标与验收、结束迭代的时间上限（用户已确认，不再单设 80 分钟上限）。每次测试设 **1 小时硬超时（3600 秒）**，到期须由 **mcn-dsh** 主动停止本轮 `rsc` 测试进程（不关闭承载 agent 的 hc 会话），以保留诊断慢阶段所需的日志。grok bot 只调度、检查状态并核验报告，不亲自执行进程终止。

三个协议都须生成 `protocol.json`、通过文件校验，并经 RFC 原文核对确认核心行为完整、没有已知的实质性错误、覆盖较基线无下降，分别记录每个协议的耗时和质量。可能目前还没有在规定时间内完成这些要求的能力，因此这就是进行这个优化循环的目睹。

## 1. 分析结果

**由 mcn-codex 完成。**

| 关注项 | 要记录的证据 |
| --- | --- |
| 时间 | 端到端耗时、当前阶段和完成批次。按 `basics` 扫描、`steps` 扫描、分类 Fix、复审、缺口修复、全局 Fix 分解墙钟时间。并行复审用请求区间的并集统计等待时间。 |

### 逐条核对 RFC

**由 mcn-codex 完成。**

由分析人员或分析 agent 读本地 RFC 原文，按章节建立一份可跨轮复用的覆盖清单。先核对核心交互，再检查本轮受影响的分支和扩展。每项同时定位到 RFC 章节或 block ID，以及模型中的实体、字段或步骤。

- **从 RFC 查模型。** 检查适用的消息、字段约束、发送和接收步骤、前置条件、状态变化、超时及错误分支。RTSP 核对会话状态与传输方式，SIP 核对事务、对话及可靠临时响应，TLS 核对两个版本的握手、密钥派生、恢复与扩展。
- **从模型查 RFC。** 检查核心步骤的角色、顺序和条件，确认字段、操作和依据相符。对适用版本、可选扩展和上层或底层负责的行为分别注明适用范围。
- **记录质量结论。** 每项标记为覆盖、缺失、错误或待核对，并给出依据。报告已覆盖项和适用项的数量，明确未核对范围。对超时或失败运行，也可用 checkpoint 判断已抽出的内容和缺口，发布验收等到完整输出后进行。

每轮分析产出一份报告，给出三协议的阶段对照、质量检查结果和下一项最值得改动的问题。运行中的报告可以先准备候选方案。

1. 从报告里选一个主要瓶颈或一组同因问题。写清楚触发条件、文件和日志证据、预计减少的请求或时间，以及需要保持的覆盖项。**每个设计给 2–3 个候选方案（最多 3 个），其中 1 个必须是结构性方案**；候选是**可独立实现、独立提交、独立复测**的方案，不是同一方案的取舍变体。单列「候选方案对比」一节：改动范围、预期同阶段收益、验证成本、风险、所需轮次、是否与其他候选冲突，以及取舍依据。**mcn-dsh 在各自 worktree 中并行实现这些方案**（见下节 worktree 约定），实现与复测报告必须记录 worktree 名字。
2. **默认选择最小改动**。能删除冗余步骤、复用已有数据结构、合并重复逻辑或简化提示时先用现有机制。需要时再调整策略、添加代码、流程步骤或数据结构。对确认可退役的功能及可达成共识的非必要步骤，核对现有调用和续跑行为后移除。**例外**：当结构性方案的同阶段收益显著更高（≥2 倍局部方案收益，或能让目标阶段直接达标）时，必须论证并允许选择结构性方案；一旦升级规则要求（见下节），以结构性方案为准。
3. 用清晰的模块边界和直接的控制流实现。检查本轮生产代码的新增和删除量，说明净增的必要性及被替代的路径。长期保持代码规模基本稳定。回归验证覆盖本轮可能影响的提取、校验、历史配对与 checkpoint 续跑行为。
4. 验证通过后为本轮改进创建独立 Git 提交。在报告中记下改动内容、动机、验证结果和仍待实跑确认的假设，并用运行目录或报告路径关联本次提交；无需填写 SHA 或其他版本摘要。后续复测使用同一次提交的代码；工作区有并行编辑时，使用隔离工作树。仅提交本轮相关改动。

### 局部微调收益台账与结构性升级

**每个设计必须给 2–3 个候选方案（最多 3 个），其中 1 个是结构性方案**（改分批策略、并发/预取、工具契约、阶段划分或提示组织等跨模块调整），其余可以是局部微调；这些候选可并行实现与复测，对比内容见上一节第 1 条。

**收益台账**：每轮分析与每份阶段性总结必须统计最近若干轮局部微调的累计收益，包括目标阶段的同阶段墙钟、请求数、输入输出、首小时完成批次、是否发布，并判定该轮**是否取得有效进展**。满足任一即算有效进展：

- 该轮设计声明的目标指标达成；
- 目标阶段同阶段墙钟或请求数改善 ≥5%；
- 首小时完成批次较上一轮增加；
- 端到端发布并通过文件与 RFC 校验。

**升级规则**（R = 连续无有效进展的轮数）：

| R | 对设计的要求 |
| --- | --- |
| 0–1 | 默认局部微调；结构性方案可选用，收益显著更高时须论证并优先选择 |
| 2 | 结构性方案必须列为**主方案**；若仍选局部方案，须逐条论证结构性方案为何不可行或收益不足，并给出下次触发条件 |
| ≥3 | 下一轮为**强制结构性轮**：主改动只能是结构性方案（可含必要小修补），局部微调不得作为主改动；单独提交，先离线回放验证再复测 |

**结构性方案门槛**：必须能用现有日志离线回放或小样本验证核心逻辑；一次不得同时改变两个以上阶段的行为；涉及工具契约或 checkpoint 结构时，必须先写兼容与续跑方案。

**计数器维护**：每份分析/阶段总结末尾写明“当前升级级别与依据”，并带入下一轮任务文档；出现有效进展即清零。R 由调度方依据已完成的复测轮次核算，mcn-codex 在报告中复核。

### 并行方案与 worktree 约定

**同一轮内最多 3 个方案并行实现与复测。** 由 mcn-dsh 在 `mcn-fuzzer` 仓库内为每个方案创建独立的 Git worktree，用于隔离实现、提交与运行；mcn-codex 的改进方案、mcn-dsh 的实现/复测报告、mcn-codex 的分析报告都必须写明所用的 worktree 名字。

- **只给 `rsc` 建工作树**，不得为整个 `mcn-fuzzer` 建工作树；工作树放在仓库内被忽略的 `.worktrees/` 下，只检出 `rsc/`，并排除 `rsc/runs/`、`rsc/.venv/`、`rsc/.tmp/` 等输出与运行环境目录，避免把运行产物复制进工作树。
- **命名**：`wt<round><字母>`（如 `wt009a`、`wt009b`、`wt009c`），分支 `exp/wt<round><字母>`；基线为该轮指定提交，或上一轮胜出 worktree 的提交（后续在其上继续改进时）。
- **提交**：每个 worktree 内的实现独立提交，报告写明 worktree 名、分支、基线提交、本轮提交号。
- **运行目录**：一律写到主仓库的 `rsc/runs/...` 绝对路径（用 `--task-dir`），不得落在工作树内；RFC 输入引用主仓库的 fixtures 绝对路径，避免重复拷贝。
- **执行方式**：在容器内以该工作树的 `rsc` 为工作目录，用主仓库 venv 的 Python 加载该工作树的包（`PYTHONPATH=.` 加 `from rsc.cli import main; main()`），确保跑的是工作树代码而不是主仓库代码。
- **并发上限**：同一时刻运行中的 `rsc extract` 进程数 = **要跑的 worktree 个数 × 3**（每个 worktree 各跑 RTSP、SIP、TLS 三个协议，每协议一个进程）；不在跑方案的 worktree 不占额度，额外诊断运行单独计数并在任务文档里写明。设计文档必须给出本次并发的 worktree 数与总进程数。
- **收尾**：每轮分析比较各 worktree 的复测结果，选出胜出方案合入 `main`；未胜出的工作树**保留**（不删除），可在其上继续改进并从该树派生新的工作树；在任何树上的新方案同样最多 3 个并行。阶段总结必须列出本阶段创建过的所有 worktree 及其去向（合入/保留/淘汰）。
