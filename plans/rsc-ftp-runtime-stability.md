# 将 FTP RSC 耗时稳定控制在 20 分钟以内

> 状态（2026-11-10）：原优化任务已由用户停止并清除，尚未达到验收目标。
> 第 23 轮按用户要求中止，不能记作完整计时结果。下文保留原计划和实验历史。
> 本次代码精简移除了来源预计划、reviewer 提前准备、来源事实共享及构建窗口提示；
> 保留批量报告、原子回滚、证据/引用校验、完整阅读和独立 review。
> 并行 parse/review 与增量复审仍是后续设计，尚未实现，也未重新启动性能实验。

## 目标与基线

使用 RFC 959、RFC 3659，以及 `gpt-6-luna / high`，持续进行分析、修改和真实测试，直到**连续 3 次完整运行均小于 20 分钟且质量验收通过**。

已有记录显示：两次运行约为 32 分钟和 56 分钟，其中 parse 从 14 分 28 秒增加到 31 分 47 秒。MCP 工具执行合计仅约 80 秒，主要波动发生在模型处理、重复阅读和校验失败后的往返。

## 提示词与工具调整

- 保留现有 **18 个工具的名称和数量**，修改参数、返回值和实现；保留旧单条调用方式。
- 合并重复提示词规则，按 preprocess、parse、review、repair 下发当前阶段的操作流程。明确完整窗口交付和凭证缓存，并对比逐窗口建模、完整阅读后统一建模的工作顺序；所有批次仍须有完成的提取和独立报告。交接后结束当前 turn，不轮询、不自行等待下一阶段。
- `read_batches` 支持读取 assignment 内不连续的证据批次，返回完整交付批次、未交付批次和 receipts；继续保证未完整交付的内容不能获得阅读凭证。
- `complete_batch`、`complete_review_batch` 增加批量提交形式。服务按 assignment 顺序保存报告，允许独立报告以不同顺序到达；整批校验失败时不部分提交。每个必需批次仍须有完整 receipt 和报告。
- 在源文本返回中提供可直接复制的 `{batch_id, block_id}` evidence；为 evidence 参数补充明确 schema。校验失败时返回错误位置、block 所属批次、当前 revision 和可执行的纠正信息，保留严格归属检查。
- `apply_changes` 返回修改记录的简洁名称与 ID 对照，减少 agent 为查找刚创建记录再次读取模型。提示词要求复用返回结果，并按阅读窗口提交相关修改。
- `query_model` 保持无损 compact 分页，增加按 evidence 批次筛选的能力，减少 parser/repair 的无关读取。Reviewer 每轮仍完成现有要求的完整模型读取；后续轮次仍读取完整 diff、指定来源和 resolutions。
- `workflow_status`、阶段提交结果明确返回当前角色是否还有工作、下一待处理批次和结束当前 turn 的指示，减少重复状态查询。

主要修改集中在 RSC supervisor 提示词、workflow tools 契约和 workflow state 实现；同步更新 `prompt.md`，避免规则冲突。

## 分析与迭代测试

1. 从现有两次运行提取阶段耗时、有效工具往返、拒绝原因、分页次数、重复读取量及可获得的模型 usage；区分 supervisor 观察与 agent 自发轮询，不能将所有空闲时间直接归为模型推理。
2. 先落实顺序/证据错误修复、批量报告和阶段提示词调整，运行针对性测试，再进行真实 FTP RSC。
3. 每次使用全新 task、独立输出目录和两只独立 Codex 会话；固定 RFC 内容、模型、effort、最多 5 轮 review，以及初始 source batching 参数。记录实际源码版本和配置，避免误测旧镜像代码。
4. 每次结束后按阶段对比耗时及往返次数，优先修改占时最大的重复阅读或 agent 循环。以实测为依据调整完整批次的阅读窗口：已对比 8,000 / 16,000 tokens；模型与 diff 分页维持 24,000 tokens。
5. 任一次达到 20 分钟仍未发布，记录为性能失败并保存现场；完成当前分析所需的日志采集后结束该测试，调整后用新 task 重跑。失败不能计为成功或靠提前发布达标。
6. 每次修改重新累计连续通过次数，直到同一版本连续 3 次满足要求。持续保存每轮分析、改动、时间与质量结果。

## 正确性与验收

- 针对批量报告原子性、幂等提交、乱序完成、不连续证据读取、错误 evidence、分页 revision、receipt 归属和阶段交接补充回归测试；运行现有 workflow、MCP、分页和 supervisor 相关测试。
- 保留独立 reviewer、来源覆盖、schema/reference 校验、证据和 resolution 验收；不通过减少 review 上限、跳过必读内容、截断模型或限制记录数量获取速度。
- 检查 FTP 控制/数据通道、active/passive、STOR/APPE 的 EOF 关闭方向、MLSD、续传和第三方传输等已暴露问题，避免优化后遗漏。
- 原文确有歧义时允许 evidence 支持的 unresolved，并单独报告 `meta.complete`；不把 published 等同语义完整。
- 20 分钟从 RSC CLI 启动计至成功发布，包含 agent 启动、预处理、解析、review 和 repair；使用正常的 SQLite 预初始化，单独记录其耗时。既有 fuzz 任务不纳入本次计时。
- 最终交付修改代码、回归结果、全部实验记录，以及同一版本连续 3 次低于 20 分钟的真实运行证据。若出现外部 API 故障，明确记录原因，不将其隐去或计作成功。

共享值字段与精确 name 选择器，保留旧格式与完整校验；工具数仍为 18。

对于来源要求的新传输生命周期，明确使用不同 channel.name 和 step.channel_name。
