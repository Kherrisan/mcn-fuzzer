# RSC 协议提取迭代计划

你是一个多 agent 任务调度者，负责协调整个 rsc 自动优化循环过程中的各个步骤，你不需要完成具体的任务，你只需要关注 2 个 agent 他们的任务完成情况，并且将任务发送给他们。

2 个 agent 角色，通过 hc 向他们发送要求，获取他们的状态和响应消息：
- mcn-dsh：负责代码实现，测试运行。
- mcn-codex：负责结果分析，设计代码改动的方案。

每个任务的产物都要保存下来，以便后续核验。

## 目标

反复执行「分析结果 → 修改并提交代码 → 并行复测 → 分析新结果」。RTSP、SIP、TLS 各自争取在 **1 小时左右**完成提取和发布，验收上限为**每个协议 80 分钟**。每次测试仍设 **2 小时硬超时**，以保留诊断慢阶段所需的日志。

三个协议都须生成 `protocol.json`、通过文件校验，并经 RFC 原文核对确认核心行为完整、没有已知的实质性错误、覆盖较基线无下降，分别记录每个协议的耗时和质量。可能目前还没有在规定时间内完成这些要求的能力，因此这就是进行这个优化循环的目睹。

第一轮直接从现有运行结果开始。最新复跑中，RTSP 和 SIP 达到 2 小时上限，TLS 在约 118 分钟时因全局校验失败退出。分类 Fix 的提示和回包已缩短，但串行扫描、长写入参数、上下文超限重试和复审后的串行补缺仍占用大量时间。该批结果可作性能诊断基线。[复跑报告](../rsc/runs/context-budget-high-20261124T071546Z/report.md) · [历史运行日志](../rsc/runs/sweep-2h-high.log) · [上下文优化计划](rsc-extract-context-budget.md)

## 1. 分析结果

**由 mcn-codex 完成。**

读取每个协议的 `run.log`、`llm/**/*.jsonl`、`extract-checkpoint.json` 和 `source-plan.json`。已发布时读取 `protocol.json`。运行中按采样时刻报告进度，给在途请求标记已等待时间，并从 checkpoint 读取实体统计。结束后补齐退出状态和质量结论。

| 关注项 | 要记录的证据 |
| --- | --- |
| 时间 | 端到端耗时、当前阶段和完成批次。按 `basics` 扫描、`steps` 扫描、分类 Fix、复审、缺口修复、全局 Fix 分解墙钟时间。并行复审用请求区间的并集统计等待时间。 |
| 模型用量 | 按阶段统计请求数、工具调用数、输入、缓存读取、未缓存输入和输出 token。总量按输入加输出计算。单独列出超时或缺少 usage 的请求。 |
| 实体与结果 | 按类型统计去重后的实体数，并记录开放问题、覆盖缺口和校验问题的变化。跟踪是否发布、文件校验结果，以及失败协议的最后阶段、退出码和具体错误。 |
| 慢操作 | 对耗时最长的阶段，列出有代表性的请求、批次或 Fix 轮次。用调用 ID 配对回包，查找重复查询、翻页往返、参数错误、修复被拒、整批重试及大提示、大回包、长写入参数。给出次数、可归属的耗时和日志位置。 |

一次往返包含多个工具时，耗时记到请求或调用链。区分模型请求等待、请求间的本地处理及重试等待。对照前一轮的同一阶段，同时看请求数量和单次请求耗时，避免把 token 降幅直接换算成耗时收益。

### 逐条核对 RFC

**由 mcn-codex 完成。**

由分析人员或分析 agent 读本地 RFC 原文，按章节建立一份可跨轮复用的覆盖清单。先核对核心交互，再检查本轮受影响的分支和扩展。每项同时定位到 RFC 章节或 block ID，以及模型中的实体、字段或步骤。

- **从 RFC 查模型。** 检查适用的消息、字段约束、发送和接收步骤、前置条件、状态变化、超时及错误分支。RTSP 核对会话状态与传输方式，SIP 核对事务、对话及可靠临时响应，TLS 核对两个版本的握手、密钥派生、恢复与扩展。
- **从模型查 RFC。** 检查核心步骤的角色、顺序和条件，确认字段、操作和依据相符。对适用版本、可选扩展和上层或底层负责的行为分别注明适用范围。
- **记录质量结论。** 每项标记为覆盖、缺失、错误或待核对，并给出依据。报告已覆盖项和适用项的数量，明确未核对范围。对超时或失败运行，也可用 checkpoint 判断已抽出的内容和缺口，发布验收等到完整输出后进行。

每轮分析产出一份报告，给出三协议的阶段对照、质量检查结果和下一项最值得改动的问题。运行中的报告可以先准备候选方案。

## 2. 修改并提交代码

1. 从报告里选一个主要瓶颈或一组同因问题。写清楚触发条件、文件和日志证据、预计减少的请求或时间，以及需要保持的覆盖项。
2. 选择最小改动。能删除冗余步骤、复用已有数据结构、合并重复逻辑或简化提示时先用现有机制。需要时再调整策略、添加代码、流程步骤或数据结构。对确认可退役的功能及可达成共识的非必要步骤，核对现有调用和续跑行为后移除。
3. 用清晰的模块边界和直接的控制流实现。检查本轮生产代码的新增和删除量，说明净增的必要性及被替代的路径。长期保持代码规模基本稳定。回归验证覆盖本轮可能影响的提取、校验、历史配对与 checkpoint 续跑行为。
4. 验证通过后为本轮改进创建独立 Git 提交。在报告中记下提交 SHA、改动摘要、动机、验证结果和仍待实跑确认的假设。后续复测使用这个提交；工作区有并行编辑时，使用隔离工作树。仅提交本轮相关改动。

第一轮优先核实两类证据充分的问题：历史不足以同时达到两个 25% 下限时，批次重试是否会在同一 checkpoint 上重复失败；扫描和补缺中的长写入参数、重复校验和重读是否能合并。先验证可节省的往返，再决定代码变更。若要改动此前确认的上下文保留规则，先记录需要决定的取舍。

**修改并提交代码由 mcn-codex 进行规划，然后将规划发送给 mcn-dsh，尤其进行代码实现、小问题修补和提交。**

## 3. 并行复测

**由 mcn-dsh 完成。**

- 输入固定为数据集中的 RTSP（2326、7826）、SIP（3261、3262、3264、3311、3326）和 TLS（5246、6066、7301、8446）HTML。保留输入顺序和 SHA-256，以便新旧结果可比。[RFC 数据集](../rsc/tests/fixtures/profuzzbench-rfc/README.md)
- 同时启动 **3 个 `rsc extract` 进程**，每个协议一个。沿用 `extract.2h-high.toml`，使用 `gpt-6-luna`、`effort = "high"` 和每个进程的 `review_concurrency = 3`。在容器内执行，每个进程从启动计时，**到 7200 秒强制结束**。记录退出码和到期状态，并确认超时进程已退出。[测试配置](../rsc/extract.2h-high.toml)
- 每轮为三个协议创建新的运行目录。保存提交 SHA、命令、配置、RFC 文件摘要、起止时间、退出原因、checkpoint、会话日志和生成文件。续跑仅用于诊断，单独标记。每个成功输出再执行 `rsc validate protocol <运行目录>/protocol.json`，随后逐条核对 RFC。
- 三个协议退出后汇总同一提交的结果。可在复测过程中预读日志和 RFC，但本轮三协议使用同一份代码。模型服务或环境故障单独记录，复测时使用新目录并保留原记录。

## 编排与验收

**编排由 grok bot 完成**

每轮在 `rsc/runs/` 下维护一个 Markdown 报告，记分析、提交和复测的状态，并链接已有产物。脚本负责统计与测试进程，agent 负责 RFC 原文判断和代码改进。通过宿主机 `hc` 向 `mcn-dsh` 等 agent 交接，项目命令仍经 `docker exec atropos-libafl-nyx`。[工作区约定](../AGENTS.md)

分析报告确定改进项后派发代码任务。有提交和回归结果后启动复测。三个进程退出后自动开始下一次分析。恢复时从已有提交、运行目录和进程状态判断哪一步待完成，避免重复提交或启动重复测试。遇到需要变更质量标准或已确认规则的取舍时，报告中记录具体决定，继续做独立的分析工作。

- **接受本轮改进**时，对照上一轮同配置结果，确认目标瓶颈有改善，且文件校验和已核对的 RFC 覆盖无退步。第一轮若没有完整质量基线，先建立覆盖清单并标出已有缺口。
- **继续下一轮**时，从本轮实际最长的阶段选下一项。对超时、失败和已有缺口保留诊断结果。若出现由本轮改动引起的质量回退或明显变慢，调整或撤回有问题的改动后再测。
- **结束迭代**时，RTSP、SIP、TLS 在同一轮均成功发布，文件校验通过，核心清单完整且没有已知的实质性错误，三者各自在 90 分钟内完成。报告每个协议距离约 60 分钟目标还有多少，并给出对应的提交和运行目录。
