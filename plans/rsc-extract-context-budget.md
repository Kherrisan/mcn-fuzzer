# RSC Extract 上下文优化计划

## 目标

缩短 Fix 提示和工具回包，减少模型反复读取的内容。宿主继续用完整 registry 做校验，保留问题、证据和 checkpoint。

当前基线来自 8 个协议的 high sweep。RTSP 的 `validate-steps-2` 首次请求用了 **162,767 输入 token**。这批最大的 `get_entity` 和 `validate_entities` 回包分别约 **137k** 和 **64k token**。扫描的缓存读取占输入 token 比例，同批内为 **89.3%**，跨批为 **44.9%**。[批次日志](../rsc/runs/sweep-2h-high.log) · [RTSP 会话](../rsc/runs/pfb-RTSP-high-20261123T172142Z/llm/category/steps/validate-steps-2.jsonl) · [回包统计](../.tmp/rsc-prompt-sizing.py) · [前缀统计](../.tmp/rsc-scan-prefix.py)

## 1. 缩短工具回包

| 工具 | 改动 |
| --- | --- |
| `search_entities`、`list_entities` | 默认给 ID、类型、名称、命中的别名和前几条证据定位。按 batch 查询时，附关联步骤总数和前几条摘要，完整列表另行分页。 |
| `get_entity`、`read_source` | 实体按 ID 和所需字段读取，默认给证据定位。RFC 正文按 `document_id` 和 `block_id` 读取，支持批量读取和续页。 |
| `validate_entities` | 默认给全局计数、当前组的问题和校验变化。问题详情按组、类型或实体分页，保留问题 ID、字段路径及已有证据定位。 |
| `complete_fix` | 返回验收结果和前后阻塞数。被拒时附简短诊断和续读入口，详情复用校验分页。 |

按实际序列化 token 限制每页大小，也限制一轮并行调用的回包总量。超限返回明确的续读位置。分页期间模型数据变动时，从新快照继续读取。整表替换前要读全相关字段。

**实现细节**

- 在 [tools.py](../rsc/rsc/extract/tools.py) 复用一个按 token 装页的函数。先确定稳定顺序，再逐条加入，给 `next_offset` 预留空间。先用 **2k token** 的索引页和 **8k token** 的详情页，`max_tokens` 可以请求更小的页。一轮并行读取共享剩余预算，优先保留写入回执和错误。延后的读调用仍返回与调用 ID 对应的续读位置。
- 保留已有的 `offset` 和 `limit`。可变数据的每页回包加 `snapshot`，续页带回它并使用相同筛选项。成功修改 registry 后换新快照，旧游标提示从新快照重查。RFC 续页只依赖冻结的来源和所请求的范围。
- `get_entity(id/ids, fields=…)` 支持字段路径，例如 `processing.on_receive`。省略 `fields` 时读完整实体定义，证据默认给定位，引用关系按需取。定义太大时给字段级续读入口，列表字段拆页时给明确的结束标记。`read_source` 可按一组 `(document_id, block_id)` 取原文，同页重复 block 只交付一次。
- `validate_entities` 和 `complete_fix` 共用紧凑诊断。问题行保留 ID、描述、类型、实体 ID、字段路径及已有的 `(document_id, block_id)`。建议和证据详单按问题 ID 取。全局计数始终来自完整校验，分页只控制回传范围。

## 2. 分类 Fix 按组处理

- `basics` 和 `steps` 的 Fix 都按共同修复位置分组。例如，同一消息缺字段引发的多条步骤报错放一组，同一通道的连接动作缺口放一组。用 `check_refs` 把开放的 `unresolved` 关联到对应检查。组太大就分页。
- 首条提示只带可写类别、全局计数、组目录首页和当前组首页。实体详情和证据原文按需读取。归并重复规则，把固定说明放前面，当前批次或组的内容放后面。
- 一轮 Fix 可以修多个组。修改后重新做全量校验，刷新组内问题和新增错误。证据不足的组可以先跳过，仍活跃的阻塞项照常计数。单轮提交继续以全局阻塞数下降或清零为准。续跑从 checkpoint 里的 registry 重算分组。

**实现细节**

1. 在 [runner.py](../rsc/rsc/extract/runner.py) 的 `validate_category` 生成分组。用消息、通道或状态的实体 ID 作组键，缺少明确目标时用问题的首个相关实体。覆盖检查沿用 `check_ref`，开放项沿用 `U…`，结构问题用规则、实体和字段路径标识。一个开放项关联多组时共享原 ID。按组内阻塞数排序，数量相同按组键排序。
2. `prompt` 只拼固定规则、全局计数、组目录首页、首组选中问题和必要字段。宿主提示先读相关字段和 RFC，再写入，再校验。一轮内用 `validate_entities(view="groups", offset=…)` 翻组目录，用 `group_id` 读取组内问题。续页带 `snapshot`。修改后用新快照返回当前组剩余问题以及新增、消失的 ID。
3. 沿用一次 `complete_fix` 对应一轮的调度。组内的修复和分页共用本轮预算。提交时宿主重算全局阻塞数。换组和刷新诊断不会增加分类修复轮数。跨组复用仍受当前 kind 的可写类别约束。

## 3. 压缩会话历史

工具回包在首次生成时按第 1 节控制长度。正常请求只追加新消息，历史中的工具调用和回包原样保留。只有上下文预算不足时才压缩历史。

1. **记录消息归属。** Scan 消息标注 batch ID，Fix 消息标注轮次 ID。一轮 Fix 内的翻页、换组和提交重试沿用同一个 ID。历史可以保留多个已完成的 batch 或 Fix 轮次。
2. **丢弃最旧的历史，至少 25%。** 从最早已完成的 batch 或 Fix 轮次开始整组移除，保留简短的进度和决定摘要。
3. **压缩接下来最旧的历史，另至少 25%。** 从丢弃后剩余的已完成历史中按时间顺序选取，替换成精简格式。工具调用和回包保留配对的 ID、工具名、状态、必要字段和重读入口。
4. **其余消息原样保留。** 两个 25% 都以配置的上下文窗口为基数，用处理前的消息 token 数计，两部分互不重叠。窗口为 258,400 token 时，至少丢弃 64,600 token 的历史，并精简另外至少 64,600 token 的历史。把摘要和精简后的消息一起计入新请求的预算。

**实现细节**

- 给 checkpoint 的每条历史记录补上 `phase`、`kind`、`assignment_id`，沿用 `messages`、`tokens` 和 `decision`。一个 Scan batch 或一次 Fix 对应一条记录。送入模型前才展开成消息列表。Pydantic AI 可能把上一轮回包和本轮提示合在一条请求里，保存时按工具调用 ID 保留调用和回包的原归属。每个阶段沿用自己的历史，完成时和 registry 一起写入 checkpoint。旧 Scan checkpoint 继续使用既有行边界，旧 Fix 从可用的 checkpoint 状态开始记录历史。
- 由 `ContextBudget` 统一判断超预算。正常路径仅展开并追加，去掉按 `keep_full_turns` 改旧回包和批次保存时压缩回包的操作。预算不足时先选最老的整组历史用于丢弃，再选紧接的历史用于精简。两组各用处理前的 token 数累计，下限都是 `ceil(context_tokens / 4)`。先算候选结果，再把摘要、工具定义和输出预留一起纳入预算复核。正在处理的记录和其余历史都保持原样。
- 精简时保留工具调用和回包配对，长正文换成带定位和续读信息的短回包。字段详情或 RFC 原文按引用重读。若已完成历史不足以同时达到两项下限，或处理后请求仍超预算，保留 checkpoint，沿用现有超预算处理流程。日志分开记丢弃量、精简前后 token 和实际节省量。

## 4. 实施和验收

先做工具投影和分页，再接入分类 Fix 分组及提示，最后改会话历史。用现有 RTSP、SIP、TLS 日志检查三项：分页能找回全部问题、所需字段和证据；修复一个组后能按新快照重新定位问题；正常请求只追加，触发压缩时两项分别达到下限，其余历史逐条一致。再用相同配置复跑，对比首条请求、最大工具回包、累计未缓存 token、工具往返次数、耗时和最终校验结果。
